Lab Submissions

Five labs, one growing app.

Each lab added a new layer to PlantLogs — from a static screen to a fully navigable, persistent application.

01
Lab 1 — UI

Static Interface

Building PlantLogs' first screen in Jetpack Compose was my introduction to declarative UI. Reflection: coming from a more traditional view-based mindset, learning to describe "what the UI should look like" rather than "how to update it" took some adjustment, but it made the layout code far more readable.

02
Lab 2 — Interaction

State & Input

Lab 2 introduced mutableStateOf and TextFields, letting users actually type plant details into the app for the first time. Reflection: understanding how recomposition is triggered by state changes was the key concept here — once it clicked, building interactive forms became much more intuitive.

03
Lab 3 — Material Design

Visual Identity

This lab gave PlantLogs its green, nature-inspired theme using Material3 colour schemes, typography and shapes. Reflection: I learned how a consistent design system — colours, type scale, card shapes — makes an app feel intentional rather than like a collection of separate screens.

04
Lab 4 — Navigation

Multi-Screen Architecture

Lab 4 was a turning point — introducing NavController, routes, and a shared ViewModel so screens could pass data between each other. Reflection: this lab taught me MVVM in practice, and the resulting structure became the backbone that every later feature in PlantLogs was built on top of.

05
Lab 5 — Room Database

Local Persistence

Room replaced in-memory state with a real SQLite database via Entity, DAO and Repository layers, so plant records now survive an app restart. Reflection: the Repository pattern was the standout lesson — keeping the ViewModel unaware of *how* data is stored made it straightforward to later add Firebase without rewriting the UI layer.

Project Submissions

From Lab 4 to a connected, sensor-aware app.

Two milestone projects turned the lab exercises into a working application — first a navigable multi-screen app, then a fully connected system with cloud sync, live data and hardware sensors.

Project 1 · Lab 4 + Working Features

PlantLogs — Navigation & Core Features

Problem statement: Plant owners have no simple, structured way to record what they're growing, where, and how it's doing — information ends up scattered across notes apps or forgotten entirely.

  • 5-screen navigation (Home, Add Plant, Plant List, Plant Detail, Health Check)
  • Shared ViewModel state across screens
  • Editable plant and health records

Lessons learned: Structuring navigation routes and a shared ViewModel early made every later feature easier to slot in. Keeping screens small and focused on one task each kept the codebase manageable as PlantLogs grew.

Project 2 · Lab 5 + API + Sensors + Cloud

PlantLogs — Connected & Sensor-Aware

Problem statement: Even with records saved on-device, plant owners still lack live environmental context (weather), an easy way to identify a specific plant on-site, and a way to learn from how others in the community are caring for similar plants.

  • 8 screens — added QR Scan and Community boards
  • Room Database for private plant & health records
  • Firebase Firestore for community plant sharing across devices
  • OpenWeatherMap REST API for live weather and watering guidance
  • GPS location capture per plant
  • Camera sensor — ML Kit + CameraX QR scanning, auto-generated via ZXing
  • Multiple photos per plant/health record with full-screen viewer

Lessons learned: Connecting four different data sources — local DB, cloud DB, REST API and hardware sensors — through a single Repository and ViewModel showed me how much the architecture from Lab 5 paid off. The biggest real-world lesson was resilience: two of my planned third-party APIs were discontinued mid-project, which taught me to verify external dependencies early and design fallbacks (local "Care Reminders") so the app degrades gracefully.

Learning Journey

From static screens to a connected ecosystem.

Lab 1 → Project 2

My journey began with Lab 1, where I learned to build static UI layouts using Jetpack Compose — a significant shift from traditional XML-based Android development. Lab 2 introduced state management and user interaction, while Lab 3 taught me Material Design principles to make the app visually consistent. Lab 4 was a turning point, introducing Navigation and ViewModel architecture, which laid the foundation for PlantLogs as a multi-screen app. Lab 5 brought persistent storage with Room Database, transforming PlantLogs from a temporary in-memory app into one that retains data permanently. Project 2 was the most challenging and rewarding phase — integrating Firebase Firestore for community sharing, the OpenWeatherMap REST API for live weather data, GPS for location tracking, and ML Kit for QR code scanning. The biggest challenge was understanding how these different technologies — local database, cloud database, REST APIs, and hardware sensors — connect through the Repository and ViewModel layers, and learning to adapt when external services I depended on changed unexpectedly. Looking back, I've grown from writing simple static screens to building a fully functional, sensor-aware, cloud-connected mobile application that supports SDG 15 by helping users monitor and care for the plants in their environment.
